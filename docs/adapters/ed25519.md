## What it is

`registry_adapters/ed25519_verifier.py` implements the existing `SignatureVerifier` protocol of `registry_successor.verify`:
`verify(alg, public_key, message, signature) -> bool`. It sits outside the registry core (contract R9). The core never imports it, and the adapter never imports the core. The caller injects it, as it injects any verifier.

- **Verifier: PyNaCl 1.6.2** (with `cffi` 2.1.1 and `pycparser` 3.12), pinned with hashes in `requirements-ed25519.lock.txt`. PyNaCl wheels bundle libsodium; the version string is not exposed by PyNaCl at run time, and the source tree PyNaCl 1.6.2 builds (its sdist, sha256 `018494d6d696ae03c7e656e5e74cdfd8ea1326962cc401bcf018f1ed8436811c`) declares **libsodium 1.0.20** (`configure.ac`; the bundled `ChangeLog` begins `Version 1.0.20-stable`). The wheel was built from that tree (its debug strings name `src/libsodium`); that is the evidence, not a runtime read.
- **No other runtime dependency.** `cryptography` is not a runtime dependency and is not imported by the adapter (a test enforces this). It remains only as a **test-only** comparison oracle and for the characterization of the raw backend, hash-locked separately in `requirements-ed25519-test-oracle.lock.txt` (`cryptography` 50.0.1 with the same `cffi` and `pycparser`).
- Lock provenance: `uv pip compile` with `--universal --generate-hashes --python-version 3.11 --no-annotate` over the single input `pynacl==1.6.2` (and `cryptography==50.0.1` for the test-only file); the hashes are the sha256 values PyPI publishes. Both install with `python -m pip install --require-hashes -r <file>` in a clean virtual environment. CI installs both in one step after the S01 lock.
- Removed: all hand-written big-integer curve code (`_decode_point`, `_add`, `_small_order`, `_D`, `_I`, `_P`, `_L` checks). The module contains no curve or field arithmetic, no point decompression and no byte-level re-implementation of a cryptographic check (a test enforces the absence of `pow` and of those names).
- Signing domain: the adapter verifies the `message` it is given and neither adds nor strips a domain prefix. The registry core implements **only** the `r08-v1` signing input (`registry_successor/selection.py`, `SIGNING_DOMAIN = b"ocs-reg/r08-v1/selection\n"`). `docs/r08-v2-contract.md` (section 1) specifies that the `r08-v2` signing input is `b"ocs-reg/r08-v2/selection\n" + canonical_bytes(statement)`; no `r08-v2` signing input or verification path exists in the core, and this PR adds none. The adapter tests build messages with both prefixes as test-local constants and show only a property of Ed25519 itself: a signature over one byte string does not verify over a different byte string. That is consistent with, but does not demonstrate, the contract's statement that a v1 signature never verifies a v2 statement; the contract property rests on the (unimplemented) v2 entry point. Nothing here is evidence of `r08-v2` end-to-end behaviour, and no claim about which work item will implement the v2 signing input is made.

## Verification policy

Name: **strict, cofactorless Ed25519 verification as implemented by libsodium, with a prime-order-subgroup requirement on the public key.**
`verify` returns True only if both library calls succeed:

1. `nacl.bindings.crypto_core_ed25519_is_valid_point(public_key)`: the key encoding is canonical (`y < p`), decodes to a point on the curve, is not one of libsodium's small-order encodings (this excludes the identity), and lies in the prime-order subgroup.
2. `nacl.bindings.crypto_sign_open(signature || message, public_key)` (libsodium `crypto_sign_verify_detached`): `S < L`; `R` is refused if small-order (identity included); and `[S]B - [h]A` is encoded and compared byte for byte with `R`, so the equation is the cofactorless one and a non-canonical `R` can never match.

| Requirement | Enforced by | Verified by |
|---|---|---|
| valid signatures verify | library (2) | RFC 8032 section 7.1 vectors 1-3, 40 honest keys, Wycheproof 117 valid |
| identity and every small-order public key refused (also all `y+p` aliases) | library (1) | all 48 encodings x 48 R x 6 S x 2 messages; identity universal-forgery tests; Wycheproof |
| non-canonical public key refused | library (1) | all 40 non-canonical encodings |
| public key in the prime-order subgroup (mixed-order refused) | library (1) | 7 mixed-order keys, one per non-identity torsion point, each with a signature that libsodium's signature check alone accepts |
| small-order R refused, identity included | library (2) | honest key with R = identity and its aliases (equation holds, library refuses) |
| non-canonical R refused | library (2), by the re-encoding comparison; never separately demonstrable (see Evidence) | all 40 non-canonical encodings as R |
| `S >= L` / malleability refused | library (2) | S+L, S+2L, S with bit 255, L, L+1, 2^256-1 (the equation holds mod L for S+L, so only the range check refuses it) |
| invalid and malformed encodings refused | library, plus the adapter's exact length and type envelope | flipped bits, truncations, wrong types and lengths, boundary shift |
| verification deterministic | libsodium | repeated calls and fresh instances |
| signed-message semantics unchanged | adapter passes `message` through untouched | adapter-level different-prefix tests (both prefixes are test-local constants; byte-string property only, not r08-v2 behaviour); end-to-end through the core for the v1 signing input only |

Byte-level checks in the adapter: **only** the envelope: `alg` is exactly the `str` `"ed25519"`, `public_key`, `message` and `signature` are exactly `bytes` (not subclasses, `bytearray` or `memoryview`), `len(public_key) == 32` and `len(signature) == 64`. The length check is load-bearing, not cosmetic: the library verifies `signature || message`, so without it a 63-byte "signature" could borrow a byte from the message (a test shifts the boundary and fails the build if the check is removed). There is no hand-written check of `y < p`, `S < L` or small order: the library does each of them, and tests prove it by example (S+L, identity R) rather than assuming it.

Failure handling: any exception from either library call (`BadSignatureError`, `ValueError`, native faults) returns `False`; `verify` never raises for ordinary input. If PyNaCl cannot be imported, or libsodium lacks the ed25519 point API, `Ed25519Verifier()` raises `Ed25519Unavailable`, and `load_verifier_or_none()` returns `None` (the core then refuses `verifier_unavailable`; an absent verifier is never a pass).

**Self-test.** Construction runs a known-answer test through the same code path and raises `Ed25519Unavailable` if the loaded backend does not show the semantics above: RFC 8032 TEST 1 must verify; S+L, the identity forgery, an honest key with R = identity, and a mixed-order key (all with an equation that holds) must be refused. This makes the pinned semantics a checked property at load time rather than an assumption about whichever libsodium is loaded.

Also exposed: `Ed25519Verifier.acceptable_public_key(public_key) -> bool` (rule 1 plus the type and length envelope; ONE argument) and `Ed25519Verifier.key_admission(alg, public_key) -> bool`, the two-argument policy shape the core calls (`ed25519` keys judged by `acceptable_public_key`; other algorithms are not judged, as in the core). Pass `key_admission`, never `acceptable_public_key`, to the core.

### What is stricter than RFC 8032 and the interoperability impact

RFC 8032 section 5.1.7 already requires strict decoding (`y < p`, and `x = 0` with the sign bit set is a failure) and `S < L`; those are not extra. Beyond RFC 8032, and beyond the minimum libsodium enforces on its own, the policy refuses:

- **small-order public keys, the identity included.** RFC 8032 has no such rule. Keys produced by RFC 8032 key generation (`[a]B`) are always in the prime-order subgroup, so no honest key is affected.
- **public keys with a torsion component (mixed order).** libsodium's signature check alone accepts them; the subgroup requirement refuses them. No honest key is affected. A key holder can no longer mint signatures on which a cofactored (for example ZIP215) and a cofactorless verifier would disagree.
- **small-order R.** An honest signer produces `R = [r]B`, small-order only if `r = 0 mod L` (probability about 2^-252), so honest signatures are unaffected.
- **R with a torsion component** is refused by the cofactorless equation. An honest signer never produces one.

Interoperability impact: signatures produced by standard signers over standard keys verify identically in any conforming verifier. The only signatures that verify elsewhere and not here are those from deliberately constructed degenerate keys or R values, which is the intent. A verifier using the cofactored equation (RFC 8032 permits either) agrees on every honest signature; any second verifier or batch verifier added to the registry must be tested against `tests/vectors/ed25519-security-vectors.json` and Wycheproof. The policy is not ZIP215.

The identity-key family is wider than one signature: with `A` = identity the equation reduces to `[S]B = R`, so `(R = [s]B, S = s)` verifies for every message and every `s` (the review package's `01 00*63` is the `R` = identity member of this family). The raw `cryptography` 50.0.1 backend accepts the whole family (characterization tests); neither libsodium nor the adapter accepts any member.

## Evidence

`tests/test_adapter_ed25519.py` (about 700 test items), `tests/ed25519_oracle.py`, `tests/vectors/ed25519-synthetic.json`, `tests/vectors/ed25519-security-vectors.json` (generated by `tests/vectors/generate_ed25519_security_vectors.py` with the plain-Python oracle; `OCS_ED25519_FULL_CORPUS=1` re-derives it in full), `tests/vectors/wycheproof/` (Apache-2.0 upstream file, unmodified, license and source commit `d17cc89fa5c8f4f4d378b5385ebf75da5d0926c9` recorded in `SOURCE.md`). Tests that need PyNaCl skip when it is absent; the characterization tests skip when `cryptography` is absent unless `CI=true`, in which case missing either package fails the build.

- **Wycheproof `ed25519_test.json`** (210 tests): 117 valid accepted, 64 invalid refused, 29 `acceptable` all refused. The 29 are 8 `SmallOrderPublicKey` and 21 `MixedOrderPublicKey` cases whose equation holds under the cofactored equation; Wycheproof lets a verifier choose, and this policy chooses to refuse because the public key is outside the prime-order subgroup (each is refused at the key check, asserted per case).
- **Characterization of the raw `cryptography` backend** (named `test_CHARACTERIZATION_*`, test-only lock): accepts the identity forgery for every message, accepts the `(R = [s]B, S = s)` family, and accepts some small-order-key rows the adapter and libsodium refuse. These tests only observe; the adapter is tested on its own.
- **Non-canonical encodings.** There are exactly 40 (`y >= p`: 19 values x 2 sign bits; `x = 0` with sign 1: 2). A test enumerates all of them: strict decoding refuses each; decoded leniently each is small-order or mixed-order (none is a prime-order non-identity point). So a missing canonicality check on the key cannot admit any of them (the small-order and subgroup checks refuse them), and on R a lenient decode could only matter together with the small-order check; libsodium additionally compares the re-encoded R. The consequence is that dropping only a canonicality check is behaviourally indistinguishable; that is recorded as an equivalent mutant, not hidden.
- **Cross-implementation comparison** over 27,073 rows (small-order key x R x S matrix, aliases, honest and key-holder signatures, malleation, bit flips, mixed-order keys, non-canonical encodings, bad lengths): adapter against libsodium raw, the policy oracle, RFC 8032 cofactorless and cofactored references and raw `cryptography`. Disagreements adapter vs policy oracle: 0; adapter accepts what libsodium rejects: 0; adapter accepts what an RFC reference rejects: 0. Raw `cryptography` accepts 158 rows the adapter refuses (small-order key 120, key-holder R = identity 8, mixed-order key 30; the vector-file rows also appear in the corpus, so some rows are counted twice); libsodium accepts 30 rows the adapter refuses, all mixed-order keys (the subgroup requirement). Every one of these is explained by the policy above. The bounded version runs in the suite; the full one is a reproducer of the review.
- **Mutation checks.** Policy mutants (the vector set against a verifier lacking one check, in the suite): dropping A small-order, A subgroup, R small-order or `S < L` is detected; dropping the pair (R canonical, R small-order) or (A canonical, A small-order) is detected; dropping only A canonical or only R canonical is not detectable (equivalent mutants, proven above). Source mutants of the adapter (temporary copies): dropping the key check, the signature call, the length check, the `alg` check, the exact-type check, changing the message, making the exception handler fail open, using the raw `cryptography` backend with or without the key check, and restricting the key check to the identity alone are all detected, with and without the load-time self-test.

## Composition with core key admission

Wiring (the only supported one): `verify_selection(..., verifier=Ed25519Verifier(), key_admission=verifier.key_admission, contract_version="r08-v2")`, or `verify_and_decide` with the same two arguments. Order, fixed by the core (#34, section 2.0-adapter): (1) the core's built-in `inspect_ed25519_key` always runs first on the mandatory path, whether or not a callback is given; (2) the adapter policy then runs and can only further restrict (a policy that returns anything but exactly `True`, or raises, refuses); (3) only after the whole snapshot is admitted does the core decode the signature (canonical base64 on `r08-v2`) and call `Ed25519Verifier.verify` on the core's signing input. Even if step (2) is not wired, step (3) refuses every key the adapter policy would (defence in depth, tested), so the adapter never depends on being composed. This PR changes nothing in #34's files.

Layer map, from `tests/test_adapter_ed25519_core_integration.py` (every row driven through `verify_selection` with `contract_version="r08-v2"`, the real adapter and the real pinned PyNaCl/libsodium; counts are asserted by the tests):

| Key / signature class | Refused by | Evidence |
|---|---|---|
| wrong type or length; non-canonical y (y >= p, any alias); the five small-order y values for either sign bit (all 8 canonical small-order encodings including the identity, and the x=0 sign-bit spellings) | **built-in admission (#34)**, `trust_snapshot_invalid`, cause `key_type`/`key_length`/`key_non_canonical_y`/`key_small_order` | CCTV 526 of 914, Wycheproof 8 of 29 `acceptable`, strict vectors 174 of 189, all 48 small-order/alias encodings |
| canonical y that is not on the curve; mixed-order keys (prime-order component plus a small-order component) | **the adapter policy** (`crypto_core_ed25519_is_valid_point`), `trust_snapshot_invalid`, cause `policy_refused`; built-in admission passes both classes | CCTV 360, Wycheproof 21 `acceptable` + 1 `invalid`, strict vectors: all 7 mixed-order rows |

What the pinned libsodium actually does with a mixed-order key (from `test_mixed_order_public_key_pinned_libsodium_signature_check_accepts_but_each_registry_layer_refuses`, PyNaCl 1.6.2 wheel, not from memory): a signature made for the mixed-order key `A + T` (T of order 8) over the core's own signing input, ground until `h` is a multiple of 8, is **accepted** by `crypto_sign_open` alone; `crypto_core_ed25519_is_valid_point` on the same key returns False. With built-in admission and a verifier that is libsodium's signature check alone, the core therefore ACCEPTS it end to end (the limit #34 documents). With the adapter policy composed it is refused at admission with `policy_refused`; with the adapter as verifier but no policy composed it is refused as `signature_invalid`. Mixed-order keys are the class the adapter, not the core, is responsible for.

Vector caveat: the core builds the signed message itself, so for CCTV, Wycheproof and the strict vectors the verifier is the real adapter with the message replaced by the vector's message; keys (both admission layers) and signatures (base64 round trip, authenticity loop, adapter verify) travel the real path. Real-message end to end tests (honest signatures, `S+L`, mixed-order key signed over the core's signing input) are separate.
