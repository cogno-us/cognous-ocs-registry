# Ed25519 SignatureVerifier adapter (EXT-S1-7)

Status: **IMPLEMENTED / DEVELOPER-TESTED.** Not independently qualified. **GAP-G3-07 (operational trust root) is NOT closed.** This adapter holds no key, no trust root, no key ceremony and no distribution mechanism; every key in the repository is synthetic (`SYNTHETIC-TEST-ONLY`).

## What it is

`registry_adapters/ed25519_verifier.py` implements the existing `SignatureVerifier` protocol of `registry_successor.verify`:
`verify(alg, public_key, message, signature) -> bool`. It sits outside the registry core (contract R9). The core never imports it, and the adapter never imports the core. The caller injects it, as it injects any verifier.

- Backend: `cryptography` **50.0.1** (with `cffi` 2.1.1 and `pycparser` 3.12), pinned in `requirements-ed25519.lock.txt`.
- Lock provenance: `uv pip compile` over the single input `cryptography==50.0.1` with `--universal --generate-hashes --python-version 3.11 --no-annotate`; the hashes are the sha256 values PyPI publishes (nothing hand-written). Install with `python -m pip install --require-hashes -r requirements-ed25519.lock.txt`. CI installs it after the existing S01 lock.
- Signing domain: the adapter verifies the `message` it is given. The domain prefix (`ocs-reg/r08-v1/selection\n`, `ocs-reg/r08-v2/selection\n`) is part of the core's signing input and is neither added nor stripped here, so a signature over one domain does not verify the other.

## Behaviour (fail closed)

Returns `True` only for a valid signature under an acceptable key. Returns `False`, and never raises, for:

- an algorithm string other than exactly `"ed25519"` (case, whitespace, `str` subclasses all refused);
- any input that is not exactly `bytes` (`str`, `bytearray`, `memoryview`, `bytes` subclasses, `None`);
- a public key not 32 bytes or a signature not 64 bytes;
- non-canonical S (S >= L), a non-canonical or undecodable public key or R encoding, and any **small-order public key** (including the identity). cryptography 50.0.1 accepts the identity-key forgery (R = identity, S = 0) for every message, so this refusal is load-bearing. This is stricter than RFC 8032, which does not require it;
- any backend exception (`InvalidSignature`, `ValueError`, native faults).

When the backend cannot be imported, `Ed25519Verifier()` raises `Ed25519Unavailable` (explicit). `load_verifier_or_none()` returns `None` instead; passing `None` to the core makes the authenticity layer refuse `verifier_unavailable`. An unavailable backend is never a pass.

## Tests and vectors

`tests/test_adapter_ed25519.py` with `tests/vectors/ed25519-synthetic.json` (RFC 8032 section 7.1 known answers, two synthetic keys, small-order and non-canonical encodings). Tests that need the backend skip when it is absent; the dependency-absent, hash-lock and independence tests always run. Evidence is recorded in the PR, not here.

## Not done

No operational trust root, key ceremony, key distribution, rotation or revocation procedure; no v2 signing input (EXT-S1-2 owns it); no independent qualification; no change to the core, to existing tests or to other documents.
