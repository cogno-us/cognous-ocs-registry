## Decision

1. Values are accepted only as exact Python or JSON integers (`type(v) is int`). `bool`, `float` (including `inf`, `nan`), `str`, `None`, `bytes`, `Decimal`, int subclasses and every other type are rejected, as are zero (registry input), negatives and any value above 2147483647. Rejections are typed refusals; a value is never clamped, coerced, defaulted or replaced.
2. The effective bound is `min(caller, registry)` and can only narrow. A registry value above the caller value leaves the caller value (a no-op, reported as `registry_value_not_narrowing`). Caller 0 stays 0. An invalid caller refuses and is never replaced by the registry value.
3. **The ceiling is a V1 technical representation ceiling, not an operational setting.** About 68 years is functionally no freshness bound. It does not assert that any bound near it is safe or useful, and no operational maximum is established: every age value in either repository is a synthetic fixture or the default 60 (largest 3600). An operational ceiling may be recorded later with evidence; lowering the maximum breaks stored registry values, raising it does not.
4. Code-owned safety floors and existing Control Plane enforcement are preserved: this decision validates and composes the registry side only. Clock-tolerance behaviour (a status observed up to `clock_tolerance_seconds` in the future passes; the past side has no tolerance) is untouched and host-owned. Narrower component-owned defaults are preserved because the registry can only narrow.
5. Where a freshness profile with outage extension is configured, composition belongs to the later host factory (`EXT-S3-4`): `FreshnessProfile.max_age_extension_seconds := min(original, min over classes of max(0, ceiling_c - narrowed_base_c))`, so base plus extension never exceeds the registry ceiling. Not implemented here.
6. The registry validator carries no private bound: `registry_successor/v2_age_bounds.py` copies the table above, and `tests/test_ext_s1_4_age_slots.py` fails if this table and the constants differ. That test compares the constants to this registry-hosted record only; it does not read any Control Plane file.
7. **Caller-side effect of the shared domain (review S2).** The caller domain is capped at `2147483647`, and F5 class ids must satisfy the registry token rule, while the Control Plane itself accepts any integer `>= 0` and any non-empty class id string. A Control Plane-valid caller policy that holds one age above `2147483647`, one class id that is not a valid token (a space, `*`, a control character, more than 128 characters), or more than 256 classes is refused as `composition_caller_invalid` for the **whole** policy. That fails closed, and it also means one such value or class disables F5 (or F4) narrowing for that deployment until the caller policy is brought inside the domain. This is an availability trade-off the Architect has not separately acknowledged; it is recorded here so it is not discovered in operation.
8. **Exact types for text.** Family names, the operator and every payload or caller key must be exact `str` objects (`type(x) is str`); a `str` subclass is refused rather than matched by value. Class ids are opaque exact strings with no Unicode normalization: `"\u00e9"` (U+00E9) and `"e\u0301"` are two distinct, individually valid class ids, and a registry class must match a caller class byte for byte.
9. **Bounded caller read.** A caller policy or class map is read once, at most `limit + 1` entries, so an oversized Mapping is refused without being copied in full.

## What the characterization does and does not establish

**Measured.** Control Plane source `cogno-us/cognous-control-plane@7a4bcd40b3b49e61ff3c294dcca53b52f460b22c`, real `BoundedAuthorizationWorkflow.decide()`, by `docs/ext-implementation/evidence/ext-s1-4-age-bound-probe.py` (output `ext-s1-4-age-bound-probe.out`). Interpreter and platform: the first line of the probe output records the interpreter, platform, pydantic version and Control Plane HEAD (added in review; the rest of the output is byte-identical to the earlier run). The probe was re-run unchanged under CPython 3.13.17, Linux x86_64 (glibc 2.39), pydantic 2.13.5, and reproduced the previously committed `.out` byte for byte; it was then extended with the date and C-int cases below and the committed `.out` is the output of that extended run on the same interpreter, against a read-only, unmodified Control Plane checkout at the pin. That one interpreter and platform is the whole measured population.

- Three `decide()` modes: freshness profile ON, ON with `anchor_deadline_to_inputs`, and OFF.
- Values tested: class base `ActionClass.max_status_age_seconds` and the scalars `status_max_age_seconds` and `approval_max_age_seconds` at `2147483647`, `2147483648`, `2**34`, `2**53`, `2**62`, `2**63`, `2**64` and `10**30` for the scalars; class base at `2147483647`, `2147483648`, `2*10**11`, `2.5*10**11`, `3*10**11`, `2**63` and `2**64`; grant status aged exactly `2147483647` and `2147483648`; base 60 with an outage extension composed up to `2147483647`.
- Float-versus-int age comparison (`(now - observed).total_seconds() <= max_age`, one microsecond above the bound): correct at `2**31-1`, `2**31` and `2**33`; the first wrong acceptance sampled is at `2**34`. Values between the sampled points were not enumerated.
- Date overflow: the earlier characterization report put it near 2.5e11 s. The probe now measures it for the class base: `2*10**11` and `2.5*10**11` are `authorized` in all three modes, `3*10**11` raises `OverflowError: date value out of range` with the freshness profile on and anchored (the profile-off mode stays `authorized`). The exact boundary between 2.5e11 and 3e11 was not located. Class base `2**63` and `2**64` raise `OverflowError: Python int too large to convert to C int` with the profile on and anchored (off: `authorized`). For the scalars, the anchored mode raises that same C-int `OverflowError` at `2**53`, `2**62`, `2**63`, `2**64` and `10**30`; the boundary between `2**34` and `2**53` for that path was not located, and the freshness-on and off modes stayed `authorized` at every scalar value tested. No timedelta limit was probed separately.

**Not established.** The measurement supports the chosen bound on that source head, interpreter and platform, in those three modes. It does **not** prove that every possible timestamp, deployment environment or consumer can safely process `2147483647`. In particular it says nothing about other platforms or Python builds (32-bit time or integer widths, other C-int sizes), other timestamp or datetime libraries, deployment clocks (skew, clock steps, far-future or far-past `observed` timestamps), or other consumers, including the Execution Runtime, which was not measured.

**What the ceiling is.** `AGE_MAX = 2147483647` is a chosen technical representation ceiling, not an operational freshness recommendation and not a safety certificate. About 68 years is functionally no freshness bound; no operational value is implied.

**Obligations that follow.**

1. A deployment must stay inside its own component-owned operational limits. The effective configuration remains bounded by them.
2. A hosting component MUST apply its own stricter bounds in addition to the registry value. A registry value never replaces, relaxes or widens a component-owned bound. An extremely large valid registry value cannot silently disable a stricter component-owned bound; the registry can only narrow (`min(caller, registry)`), and a registry value above the caller yields the caller value, reported as `registry_value_not_narrowing`.
3. Existing mandatory component safety bounds are unchanged by this record.

## Re-verification against source (EXT-S1-4)

Probe: `docs/ext-implementation/evidence/ext-s1-4-age-bound-probe.py`, output `ext-s1-4-age-bound-probe.out` (real `BoundedAuthorizationWorkflow.decide()` at the pin; freshness profile ON, ON with `anchor_deadline_to_inputs`, and OFF).

| class base `2147483647`, grant status aged exactly `2147483647` / `2147483648` | `authorized` / `hold` (the bound is exact at the ceiling) |
| scalars `status_max_age_seconds`, `approval_max_age_seconds` at `2147483647`, `2147483648`, `2**34` | `authorized` in all three modes |
| scalars at `2**53`, `2**62`, `2**63`, `2**64` and `10**30`, anchored | raw `OverflowError` (C int conversion); freshness on and off: `authorized` (no ceiling exists on that path); boundary between `2**34` and `2**53` not located |
| class base `2*10**11`, `2.5*10**11` | `authorized` in all three modes |
| class base `3*10**11` | `OverflowError: date value out of range` with the profile on and anchored; off: `authorized` |
| class base `2**63`, `2**64` | `OverflowError` (C int conversion) with the profile on and anchored; off: `authorized` |

| float-versus-int age test, age = bound + 1 microsecond | correctly refused at `2**31-1`, `2**31`, `2**33`; wrongly accepted first at `2**34` |

Conclusion, limited to what was run: at pin `7a4bcd40`, on CPython 3.13.17 / Linux x86_64, in the three modes, over the sampled values above, `2147483647` and `2147483648` were representable and produced no exception and the expected decision (`authorized`, or `hold` when the grant is older than the bound). That is consistent with the Architect's condition and gave no reason to narrow the ceiling in this record; it is a sampled measurement by the builder family, not independent verification and not a proof for all values or environments. The ceiling is a chosen technical bound with margin, not a source cliff. Failure points observed in the probe: the float-versus-int misjudgement first seen at `2**34` (about 8x above the ceiling; sampled, not shown absent between `2**33` and `2**34` or below), a date-range `OverflowError` for the class base between 2.5e11 and 3e11 s with the freshness profile on (roughly 116x to 140x above; exact boundary not located), and C-int `OverflowError` for the class base at `2**63` and for anchored scalars at `2**53` and above. The unanchored dispatch window can reach twice the bound (4294967294 s, arithmetic from the code reading, not probed), below `2**33`.

Not established: operational duration; behaviour of consumers with narrower integer widths; exhaustive absence of float misjudgement below `2**34`.
