## 2. Why the profile-bearing families refuse a `policy_binding` profile
Sources (read): registry_governed_policy.py:284-285 (composed workflow, `profile_families and host.policy_binding is not None` -> `policy_binding_unsupported`, boundary construction); registry_f5_class_age_governance.py:204-205 and its docstring :38-39 ("how a Registry class age feeds the generation is not decided"); registry_f5_class_unreadable_governance.py:261-262; pinned by tests/test_governed_policy_composition.py `test_c06...` (:247-253) and by mutation entries (P17, M18, M29 in the docs mutation harnesses). Stated reason: a fail-closed deferral, not a technical incompatibility. A Registry selection changes the effective profile after the host chose a binding, and nobody has decided whether that must also move `policy_generation`/`activation_ref`.

What PolicyBinding is (policy_binding.py:61-79): trusted host config `version policy-binding/0.1`, `binding_digest` (required for `selected`, absent for `withdrawn`), `selection_epoch`, `activation_ref` (sha256 digest), `policy_generation` (opaque, never derived from the epoch), `disposition` selected|withdrawn, `age_ceilings: dict[action_id, int>=1]`. `activation_sequence` is reserved and refused. Defects: policy_binding.py:127-152 (`invalid` for unknown action ids, `unanchored` when ceilings exist and freshness is missing or the flag is not True, `exceeded` when class base + `max_age_extension_seconds` > ceiling). Re-run at construction (runtime_authority.py:226) and at every evaluation (runtime_authority.py:446-453) because `model_copy` skips validators.
How it is committed:
- Field of `RuntimeAuthorityProfile` (runtime_authority.py:217, omitted while None). It is therefore inside `profile.model_dump`, so inside `catalogue_digest = commitment(profile.model_dump)` (runtime_authority.py:473).
- `approval_commitment` (runtime_authority.py:236-251): with a binding the preimage becomes the TAGGED `approval-commitment/0.2` = legacy preimage + `policy_identity` (activation_ref, selection_epoch, disposition, binding_digest) + `policy_generation`. Without it, byte-identical legacy.
- The approval's `runtime_authority` spec must carry `approval_commitment_version`, `policy_generation`, `policy_activation_ref` and they must equal the binding (runtime_authority.py:325, 455-469); the extension persisted in the decision binding carries the same members (`generation_fields`, :469-478). Missing/mismatch give typed holds (`approval_policy_generation_missing|invalid|mismatch`, `approval_policy_activation_mismatch`, `approval_commitment_version_unsupported`).
- `rule_revision` is not part of PolicyBinding or its commitment; it is the separate N2 signer set (`rule_revision_profile`) that authorizes outage age extensions (bounded.py:1358-1376). Extension authority is rechecked at each use. Do not conflate them.
- Not durable: policy_binding.py:10-18 says it has no memory; anti-rollback (a durable `scope_required` ratchet, atomic effect-time verification) is EXT-S4 and not implemented. The tests pin two negative controls (older generation revived; dropped binding revives legacy approval).
What supporting it would take: (1) a decision of what a Registry class-age selection means for `policy_generation`/`activation_ref` (does a narrowing bump the generation? who mints it?), which the families explicitly left open; (2) a host source of a real `binding_digest`, `activation_ref`, generation and v0.2 approvals; (3) lifting the refusal(s) with tests; (4) final-composition and identity handling (section 4B). Items (1) and (2) are authority-semantic and need the Architect.

### Option B: compatible `policy_binding` integration (no protected edit)
Can the anchor family be accepted only when the host already carries a PolicyBinding? Yes, and the effect is verified (section 3): the host binding alone, with the Registry-effective profile, anchors the purpose observation at the Registry-narrowed base. The Registry family would add a precondition refusal (e.g. `anchor_policy_binding_required`) when `host.policy_binding is None`, and set the flag only when the host binding is present.
Host work required: a real PolicyBinding (selected: valid non-zero `binding_digest`, `activation_ref`, generation, epoch; or withdrawn, whose representation is explicitly PROVISIONAL, policy_binding.py:21-24); approvals issued under approval-commitment/0.2 carrying the three spec members, committed against the FINAL effective profile; a freshness/0.1 profile with the flag. Every existing approval is invalidated (v0.2 tag, profile dump gains the key). `age_ceilings` may stay empty; if set it must name known action ids and base+extension must not exceed it.
Does lifting the refusal in registry_governed_policy.py:284 suffice and stay safe?
- Suffices mechanically: it is the only gate for the composed workflow. The standalone family workflows (registry_f5_class_age_governance.py:204, registry_f5_class_unreadable_governance.py:261) would keep refusing, which is fine if the anchor family is composed-only. But lifting it for ALL profile families (as a blanket removal) is a wider decision than the anchor needs: restrict it to "binding allowed iff the anchor family is declared", otherwise the generation question reopens for unrelated families.
- Composition handling (read): every composer does `host.model_dump -> edit -> RuntimeAuthorityProfile.model_validate` (compose_profile registry_f5_class_age_governance.py:116-126; compose_unreadable :145-150; compose_irreversible :113-120; compose_assurance :122-129; compose_terminal :132-138). None reads or writes `policy_binding`, so it passes through verbatim, and `model_validate` re-runs `policy_binding_defects`. Narrowing a base or capping the extension can only lower `base + ext`, so `exceeded` cannot newly fire; `unanchored` cannot fire if the host already had the flag. `final_composition_defect` (registry_governed_policy.py:127-165) ends with `dh == df` over the whole dump: an unchanged binding compares equal; any foreign change still gives `composed_profile_invalid`. No other family changes PolicyBinding, so no new interaction. The flag itself (still unimplemented) would need the `anchor_declared` carve-out recorded in the earlier reconciliation.
- NOT proven safe by the lift alone, and the reason the refusal exists: a Registry narrowing is a policy change that does not move `policy_generation`/`activation_ref`. Approval validity is still protected by the profile-dump commitment (a changed class age changes the commitment), but a revert of the Registry selection revives older approvals exactly as with the host binding rollback negative control (policy_binding.py:10-18; no durable ratchet). The pin-export path (authorization_pin_export.py:128-148) compares persisted `catalogue_digest` and generation/activation with the side's; its behaviour for a Registry-composed profile was not tested here.
- Also: the host must treat the binding as a REAL activation. Inventing placeholder digests/generations only to turn anchoring on is a fabricated authority claim and defeats the purpose of the commitment.
Verdict B: safe as an explicit host precondition and strictly additive, but it moves the Registry's guarantee onto a host feature the Architect has not finished (generation semantics, EXT-S4). It needs an Architect ruling on that semantic; it does not need F3 for an evaluator unless the lift also touches the byte-pinned files (it does not).

### Option C: alternatives without a protected-evaluator edit
C1. Control Plane wrapper at the commit gate that re-checks purpose-observation age. Feasible inputs exist: the retained effect-stage journal row for the purpose input carries `observed_at`, and for a cached snapshot `age_bound_seconds` (probe: retained input `observed = {'state','observed_at','epoch','epoch_capability'}`; cached extras from bounded.py `_cached_purpose`). The wrapper (`_GatedDestination.apply`, registry_governed_lifecycle.py:106-108, gate = `_gl_commit_gate` :207-213) would compute `observed_at + bound` against the service clock immediately before `apply`. Equivalence assessment (read, not prototyped):
  - Weaker than the evaluator: the stock gate also applies the monotonic guard and wall-clock-stepped-back guard (bounded.py:1424-1431) and pops `_mono_open` before apply (bounded.py:1785); a wrapper has no matching monotonic origin, so a stepped-back wall clock defeats it.
  - It runs after the "attempted" row is written and only produces `DefinitiveDestinationRejection(REJECTION_CODE)` (a mislabelled Registry rejection code), not `check_expired_before_dispatch`, no `expired` CheckEvent and no `EffectTimeRefusal` row; Evidence Pack refusal counts and reaper semantics would not see it. Adding a new code is a vocabulary/registry decision.
  - Coverage: only workflows built by the governed lifecycle. A plain `BoundedAuthorizationWorkflow` with the same flag and the same profile (the profile is what is committed) stays exposed, so the guarantee is not carried by the committed profile.
  - Identifying "this execute's" check from the gate (the gate takes no arguments; the journal can hold several checks per effect) is ambiguous under concurrency; fail-closed handling needed.
  - tests/test_governed_policy_composition.py `test_z04` asserts the shared lifecycle never touches a governed field and holds no policy; a temporal check there needs that contract re-reviewed.
  - Authority/commitment: adds no authority (it can only withdraw) and does not change the profile dump, but the enforcement is not committed anywhere (not in `catalogue_digest`, not in the approval): the approver cannot tell whether the stronger rule was in force. Could be added to the bound identity only, which is the same weaker class of binding the F4 scalars have (07-commitment-binding-decisions, D-06).
  Verdict: not equivalent; do not accept as the resolution.
C2. Refusal rule "the anchor family applies only if the host profile has purpose bindings anchored". The profile does not say whether grants carry a `purpose_ref`; that lives in the resolver's authority context (runtime_authority.py:~380 `grant.get("purpose_ref")`). A construction-time rule can only test `policy_binding is not None` (= Option B). A decision-time rule ("if the decision's resolution inputs include a purpose input and no binding, refuse") is implementable in the lifecycle but is a full availability loss for every purpose-bearing grant, and an authorized decision is already persisted before it can run. It is a legitimate fail-closed fallback if the Architect prefers refusal to a documented residual; it is not an "enforcement equivalent".
C3. Clamping at construction (halve the effective class base so purpose age at evaluation <= B/2 and the deadline <= opened + B/2; with an extension e use floor((B - e)/2)). Arithmetically bounds purpose age at dispatch by B for the live observation, but: it changes what the class-age family means (effective value no longer `min(host, registry)`, which derive_effective, identity and the F5 contract pin), halves availability for every input, changes the committed profile (so is an approval-changing decision), is undefined for B = 1 (needs base >= 1), and the cached snapshot bound uses `_class_age_bound` (extension-raised) so the clamp must also reason about extension arithmetic. Needs an Architect ruling; not recommended.
Overall C: no variant proves equivalent or stronger enforcement without a protected change.

## 5. Outage extensions (`max_age_extension_seconds`) versus the narrowed ceiling
- Extension arithmetic: `effective_age_bound` measures the limit from the trusted class base, never the row's own base (freshness.py:182-201); irreversible and post-reversal-window classes are never extended (bounded.py:1371-1376). Class-age composition caps the extension at `min(host_ext, registry - narrowed base)` over all Registry-named classes (registry_f5_class_age_governance.py:122-126), so base + ext <= Registry value.
- Which inputs the extension raises: grant status (bounded.py:2393-2395 uses `_class_age_bound`) and the cached-purpose bound (bounded.py `_cached_purpose` -> `_class_age_bound`, reversible only). It does NOT raise the live purpose acceptance bound, which is `cl.max_status_age_seconds` (runtime_authority.py:420 area, `age > cl.max_status_age_seconds`), nor identity/mandate/approval/conflict/policy (they use workflow scalars).
- Anchor + extension: with the flag, the deadline is `min(opened + bound_used, min_i(observed_i + bound_i))`, with `bound_used`/`bound_i` <= the Registry value by composition. So an extension cannot defeat the ceiling for anchored inputs. The residual is independent of extensions: without the purpose anchor, a cached snapshot may be accepted at age up to `base + ext` and dispatched up to `opened + base + ext` later, i.e. up to about 2 x (base + ext) <= 2 x ceiling.
- Option A anchors the cached snapshot at its recorded (possibly extended) bound, which is <= ceiling. Option B yields the same via the binding. In both, `exceeded` (binding present) additionally refuses a host whose base + ext surpasses a host ceiling.
- Unrelated limit (not changed by anything here): extension authority is asserted and unauthenticated for the cached-purpose path (comment at runtime_authority.py:414).

## 6. Recommendation and authorization boundary
1. Smallest source-backed change that preserves authority and commitment semantics: Option A (one condition in runtime_authority.py:404, plus test inversion and byte-pin update). Everything else in the anchor-family plan (composer, `anchor_declared` carve-out in `final_composition_defect`, `freshness is None` refusal, identity coverage) is unprotected Registry/CP-side work from the existing anchor reconciliation and can proceed in parallel, but must not be described as satisfying the invariant before Option A (or B) lands.
2. Requires Architect authorization AND F3 requalification: Option A (protected evaluator edit, test/pin inversion). Requires Architect authorization/decision (no evaluator edit): Option B's semantic (generation/activation meaning of a Registry narrowing; host provisioning of a real PolicyBinding); Option C2 if chosen as the policy (availability loss); Option C3 (changes the meaning and commitment of the class-age value). Any persisted-decision schema or approval-preimage change (for example to commit enforcement of C1) requires both, and was not designed in detail here.
3. If no authorization is given: the invariant cannot be met for purpose-bearing grants. The accepted-residual path must say: with the anchor family and no host PolicyBinding, a purpose observation or cached snapshot may be dispatched up to about 2x the Registry-narrowed ceiling (<= 2 x ceiling), pinned by tests/test_freshness_purpose_residual.py.
4. Do not set the flag and call the invariant resolved.
