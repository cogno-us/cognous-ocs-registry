## Answers to the specific questions
A. Deny-all representation. Payload key present with `[]` is the explicit deny-all for that dimension; an absent key is `field_missing`, never implicit allow or deny (v2_f1ab.py docstring 5-6; _list_ok 35-41 `if not value: return True`; contract s2 "An empty F1ab list is a valid explicit deny-all"). Caller side: [] also valid (normalize_caller). Composer: any empty effective set -> CompositionResult(deny_all=True, deny_all_fields=(...)) (v2_f1ab.py:96-97); decision kind `applied_deny_all`; effective-policy preimage carries `deny_all` = sorted empty dimensions, and a presented preimage whose deny_all list mismatches is field_invalid (Amendment 1 s4, rule 3; v2_policy_identity.py:1228 deny_all_dimensions). Contract s2: "Deny-all is decided by the enforcing gate before any policy object is built (D-20). The family composers never construct a Runtime policy." Contract line 177: registry_deny_all is distinct from a LocalExecutionPolicy.check denial; equivalence is asserted only for representable NON-EMPTY effective policies. Limits: the frozen S03 schema requires entries minItems 1 so S03/S04 file records cannot express deny-all (s04-implementation s6); F4/F5 have no deny-all (caller 0 stays 0, deny_all never set, v2_age_bounds.py:36). Whether Runtime's frozen constructor can be fed an empty set is a Runtime question (other worker); the S06 question stays open at the Runtime boundary.
B. Narrowing semantics. s7.4 item 3: effective_policy_digest is not compared to durable state; "the narrowing itself is enforced by the evaluator on the policy the executor was given". Amendment 3 supersedes sole reliance: for a claim with a binding, after items 1-7 and inside the same atomic transaction, each of the five sets of the effective executor policy must be a SUBSET OF OR EQUAL TO the activated record payload set; excess member -> REFUSE `policy_identity_mismatch` (cause names first offending set); payload missing/non-canonical/digest-mismatched/lacking one of five sets/malformed -> HOLD `store_unknown`; executor sets absent -> `verifier_unavailable`; executor sets not reproducing digest -> `policy_identity_mismatch`; any exception -> refuse/HOLD, never skip. Amendment 3 s3 residuals: executor honesty, max_amount/target prefixes caller-owned. Amendment 4 (pin) changes only where the scope key comes from (pin members, not claim) and states F-01 five-set containment and existing reason codes unchanged (Amendment 4 lines 33, 237). Order relation = set inclusion per key; F4/F5 = integer <= (min).
C. Versioning and family dispatch. Contract version is an exact-str switch: families.table_for_contract_version (families.py:140-149) maps only "r08-v1"->FAMILIES (1 family) and "r08-v2"->FAMILIES_V2 (4); anything else is `contract_unsupported` with no table (no fallback, upgrade or default). Record: decision.validate_record_text_v2 (decision.py:140) requires contract_version == r08-v2, kind record, family in FAMILIES_V2. A family is registered ONLY by editing families.py (FamilySpec: payload_fields, payload_validator, composer, evaluator_binding, caller_normalizer, enforcing_component) AND, separately, v2_policy_identity.IDENTITY_FAMILIES (1143-1148, derived family_version "v1"/"v2", REGISTERED_CONTRACT_VERSIONS=("r08-v2",)). Two tables must be kept in step by hand; no single test asserts their key sets are equal (tests assert each literal set). There is no per-family version field: f1ab "version" is the family id string plus the derived family_version tag. A new f1ab layout therefore means a new family id (e.g. f1abc-...) registered in both tables, or a new contract version (r08-v3) requiring table_for_contract_version, REGISTERED_CONTRACT_VERSIONS, signing domains and new reasons review. Signing input is domain-separated per contract version (v2_selection.py:22). v2 module naming: v2_f1ab.py, v2_age_bounds.py, v2_policy_identity.py, v2_selection.py, v2_codes.py, v2_token.py.
