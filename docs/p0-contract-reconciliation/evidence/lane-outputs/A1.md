## Candidate genuine conflicts / reconciliation items

None is an unambiguous incompatibility; CC-1 is the only one I would put forward for targeted adjudication.

**CC-1 Registry location/ownership vs the existing cognous-ocs-registry repository (ADR-P03).**
- V0.2 side: `m0-decision-record.md` s2 row 3 "ADR-P03 registry location: hub-owned immutable digest-pinned artifact | Approved"; `s02/m0-decision-packet.md` row 3 "If approved: No new repository or pin carrier"; `s02/adr-proposals.md` ADR-P03 "no new repository yet ... A separate registry repository can follow if requirements justify it".
- Registry side: `cognous-ocs-registry` README (Mission: its "sole development objective" is a versioned declarative registry; "What exists": `registry_contract/` record contract, `registry_consumer/`), plan v1.3 s5 "Registry: typed configuration records, validation/adapters, approval/selection/custody metadata and lifecycle contracts". The README also says it "does not ... reactivate the v0.2 program".
- Existing behavior: hub holds `ocs-registry-record/0` (rule_table of check/scanner rules, reason_map, evaluators); registry repo holds a different record family (typed config, `r08-v1`). Two record contracts, two canonicalization implementations, neither wired to a consumer.
- Consequence: P2 (R09) "record and selection authority" could be built twice, or a pin carrier added that ADR-P03 said not to add.
- Recommended resolution (smallest): record, as a P0 decision, that ADR-P03 governs the hub-resident rule/check/scanner artifact consumed by Control Plane in V0.2 and the registry repo is the authoring/custody home of V1 typed configuration records, with any pin carrier named explicitly; or alternatively that the registry repo artifact is the "digest-pinned artifact" of ADR-P03. Do not merge schemas.
- Components: hub, registry repo, Control Plane, Execution Runtime. Phase impact: P2 (record/selection), P3 (adapter inputs), P4 (activation pin carrier).

**Reconciliation items that are NOT conflicts (need an adapter or clarification, no adjudication):**
- *Two "epoch" meanings.* 1.3 s3 says `epoch` owner is "Control Plane at activation", yet 2.1 stores `epoch` as a publication-succession counter (hub store enforces strict increase). Q14 default 5: "Control Plane owns selected effective epoch". Name them differently (record epoch vs selected effective epoch). P2, P4.
- *Canonical JSON identifier.* ADR-P01 approved; 2.1 implements an RFC 8785 subset (floats, non-finite, duplicate keys refused) under identifier `rfc8785-jcs`, the same identifier as ODES's full profile (24 tests). Refusal-only difference; document the restriction as a validation rule of the registry profile and check against R08 canonicalization (lane B). P2. The ADR-P01 "profile-identity table" deliverable was not found (UNVERIFIED).
- *Conditional mandatory rules.* DGR forbids marking a mandatory check not-applicable "without a proven source predicate" (so a proven predicate is allowed); 2.1 refuses every conditional mandatory rule (`mandatory_check_conditional`). Q11 approves `/1` with closed predicate identities but nothing is implemented. Registry v1.3 must not assume conditional mandatory entries are accepted by `/0`. P2, P3.
- *Rule-set identity in decisions (FP-04).* The one contract the plan needs ("exact effective-policy identity" in evidence, plan v1.3 s3 constraint 7) has no adopted or implemented home: needs either the opt-in `{profile,digest}` context member (FP-02/04 reading, "only" contingent) or a Control Plane change. F3 is unauthorized (Q14 default 2). This is a **missing contract**, for lane C. P3, P4.
- *Stale text.* `operator-decisions.md` row "handoff versus refreeze authorship remains OPEN" vs m0 record s3-s4 ("no pin selection by the handoff") and `minimum-profile.md` "(proposed ADR-P08)" vs m0 row 7: resolved by the stated precedence rule (M0 record governs). FP count: m0 record says FP-01..05, packet says FP-01..04 (FP-05 came from AOI).
